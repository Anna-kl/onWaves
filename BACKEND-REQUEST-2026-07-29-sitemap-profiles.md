# Запрос к backend — список публичных профилей для sitemap.xml

Дата: 2026-07-29
От: фронт. Нужно, чтобы бэк добавил один read-эндпоинт (ниже — контракт, который ждёт фронт).

## Зачем

Сайт получил `sitemap.xml` (отдаётся из `server.ts`, объявлен в `robots.txt`). Сейчас в нём
**только 5 страниц витрины** — главная, лендинг, расширенный поиск и два статических раздела.

Карточек мастеров в карте нет, потому что их неоткуда взять: в API есть только точечный
`GET profiles/translate-link/{link}` и `GET search/?request={…}` по конкретному запросу.
Эндпоинта, отдающего список публичных профилей, нет.

Что это означает на практике: **карточки мастеров — это вся поисковая масса сервиса**, и сейчас
поисковик обязан находить их сам, переходами по внутренним ссылкам. Пока профиль не попал в выдачу
поиска на самом сайте, робот может не узнать о его существовании месяцами. Sitemap — единственный
способ сказать «вот все N карточек, вот когда каждая менялась».

Просьба: один эндпоинт, ниже контракт.

---

## Эндпоинт

```
GET profiles/sitemap?page={n}&pageSize={m}
```

- **Без авторизации.** Его будет дёргать наш SSR-сервер (Node), а не браузер пользователя.
- Отдаёт **только публичные** профили — те, что реально открываются по прямой ссылке анонимом.
  Скрытые / заблокированные / удалённые / незавершённой регистрации включать **нельзя**:
  каждый такой URL — это 404 или пустая страница в карте сайта, за что поисковик понижает доверие
  ко всей карте целиком.

### Ответ

```jsonc
{
  "code": 200,
  "data": {
    "items": [
      {
        "link": "anna-manicure",          // ← сегмент URL карточки, НЕ GUID (см. ниже)
        "lastModified": "2026-07-21T10:15:00Z"
      }
    ],
    "page": 1,
    "pageSize": 1000,
    "totalCount": 4820
  }
}
```

### Поля

| Поле | Тип | Обязательность | Комментарий |
|---|---|---|---|
| `link` | string | обязательно | Тот самый сегмент, что стоит в адресе карточки |
| `lastModified` | ISO-8601 UTC | желательно | Дата последнего изменения профиля |
| `page`, `pageSize`, `totalCount` | number | обязательно | Для постраничного обхода |

#### Почему `link`, а не `id`

Адрес карточки — `https://onwaves.online/{link}`, где `{link}` фронт отдаёт в
`GET profiles/translate-link/{link}` и уже оттуда получает GUID
(см. `profileba.component.ts:130`). То есть в sitemap должен попасть **`link`**.
GUID в карте сайта бесполезен: по `https://onwaves.online/{guid}` страница не откроется.

Если у профиля `link` не заполнен — такой профиль в ответ **не включать** (у него нет
адреса, который можно проиндексировать).

#### Почему важен `lastModified`

Это единственный сигнал, по которому робот решает, переобходить страницу или нет. Без него
он либо ходит по всем карточкам подряд впустую, либо неделями не видит, что мастер обновил
услуги и цены. Поле `lastModified` в модели профиля **уже есть** (`IViewBusinessProfile.lastModified`) —
нужно, чтобы оно обновлялось при изменении услуг, графика и текста профиля, а не только
при правке имени.

Если поднять его достоверность сейчас сложно — отдавайте что есть, фронт сработает и без него
(поле необязательное). Но тогда это стоит завести отдельной задачей.

### Пагинация

- `pageSize` по умолчанию 1000, максимум 5000.
- `page` с 1.
- Порядок любой, но **стабильный** между страницами (например, по дате регистрации),
  иначе при обходе часть профилей продублируется, а часть потеряется.

Ограничения формата (наши, не ваши, — просто чтобы был понятен смысл пагинации): в один файл
sitemap влезает 50 000 URL. Дальше фронт сам разобьёт карту на несколько файлов с индексом.

### Производительность

Эндпоинт вызывается редко (раз в несколько часов, результат кешируется на нашей стороне),
но проходит по всей базе. Просьба сделать его дешёвым: выборка только двух полей, без
подтягивания услуг, аватаров, отзывов и рейтингов.

---

## Что делает фронт после этого

Одна функция в `server.ts` (`buildSitemap`) — постранично забирает список, кеширует и подмешивает
карточки к пяти статическим URL. Контракт выше — ровно то, что она ожидает; ничего больше
для этого не нужно.

## Отдельно: не к бэку, но рядом (для продукта)

Найдено при разборе этого же кода, к эндпоинту отношения не имеет, но влияет на тот же трафик.

**Константа ссылки на профиль указывает на старый домен с hash-роутингом:**
`urlProfile = 'https://ocpio.ru/#/id/'` (`src/helpers/constant/commonConstant.ts:1`).

Она используется там, где мастер копирует ссылку на свою страницу
(`main-profile.component.ts:100`, кнопка «скопировать»). То есть мастера рассылают клиентам,
публикуют в соцсетях и в шапке профиля адрес вида `https://ocpio.ru/#/id/anna-manicure`, тогда как:

- рабочий домен — `onwaves.online`;
- приложение собрано с `useHash: false`, то есть маршрут `#/id/...` им не обрабатывается;
- всё, что после `#`, поисковик вообще не считает отдельным адресом — такие ссылки не приносят
  сайту ни веса, ни переходов из поиска.

Нужно решение продукта: оставить `ocpio.ru` живым и настроить с него 301-редирект на
`https://onwaves.online/{link}` (тогда старые ссылки, уже разошедшиеся по интернету, сохранят вес),
и в любом случае поправить константу на актуальный адрес без `#`. Правка на фронте
однострочная — жду подтверждения целевого домена.
