# Отправка форматов работы мастера (со стороны фронта)

Дата: 2026-07-14

Описывает, что **фронт сейчас отправляет** на бэк при сохранении форматов работы БА —
встречная часть к `frontend-card-address-output.md` (там про то, что бэк возвращает в `address`).
Актуально после перехода на модель «один формат = одна запись локации».

---

## Модель форматов

У мастера может быть несколько форматов одновременно (мультивыбор в UI). Каждый выбранный
формат отправляется **отдельным POST-запросом**. Формат задаётся числом `locationType`:

| `locationType` | Формат | Что шлём |
|:---:|---|---|
| `0` | **Fixed** — стационарно | полный адрес (город, улица, дом, квартира) |
| `1` | **Mobile** — разъездная | регион + список городов/районов |
| `2` | **Online** — онлайн | только тип, без адреса |

---

## Поток сохранения

1. `POST /v1/api/profiles/business` — создаём профиль БА. Ждём ответ `201`, берём `data.profileUserId`.
2. Для **каждого** выбранного формата: `POST /v1/api/profiles/{id}/work-location` — по одной записи на формат.
   Запросы уходят параллельно (`forkJoin`), фронт дожидается завершения **всех** перед закрытием модалки.
   Ожидаемый код каждого ответа — `201`.
3. Если хотя бы один POST локации упал — профиль уже создан, ошибка отдельной локации гасится
   (логируется), регистрацию не откатываем.

Тот же набор тел используется и в режиме редактирования (страница «Контакты» → «Сохранить»).

> Порядок формирования тел: `Online → Fixed → Mobile`, но так как POST-ы идут через `forkJoin`
> **параллельно**, порядок прихода на сервер не гарантирован. Это ок: бэк делает **upsert по
> `(profileId, locationType)`**, поэтому повторная отправка того же формата не плодит дубли.

### Заголовки
```
Authorization: Bearer <token>
Content-Type: application/json
```
(токен берётся из переданного значения либо из cookie `auth-token-ocpio`.)

## Тело запроса `POST /profiles/{id}/work-location`

TypeScript-модель (`IWorkLocation`), которую сериализует фронт:
```ts
interface IWorkLocation {
  locationType: number;          // 0 Fixed | 1 Mobile | 2 Online — обязателен
  country?:   string | null;
  region?:    string | null;
  city?:      string | null;     // только Fixed
  street?:    string | null;     // только Fixed
  house?:     string | null;     // только Fixed  (внимание: поле называется house)
  apartment?: string | null;     // только Fixed
  cities?:    string[];          // только Mobile — список городов/районов
  longitude?: number | null;     // сейчас всегда null
  latitude?:  number | null;     // сейчас всегда null
}
```

> Поля `premise` **нет** (убрано). Координаты `longitude/latitude` фронт сейчас всегда шлёт `null`.

### 1. Fixed — стационарно (`locationType: 0`)
```json
{
  "locationType": 0,
  "country": "Россия",
  "region": "Московская область",
  "city": "Москва",
  "street": "Тверская",
  "house": "12",
  "apartment": "45",
  "longitude": null,
  "latitude": null
}
```

### 2. Mobile — разъездная (`locationType: 1`)
Список городов/районов в `cities`; полей `city/street/house/apartment` нет.
```json
{
  "locationType": 1,
  "country": "Россия",
  "region": "Московская область",
  "cities": ["Балиха", "Ступино", "Изюх"],
  "longitude": null,
  "latitude": null
}
```

### 3. Online — онлайн (`locationType: 2`)
Только тип.
```json
{
  "locationType": 2
}
```

### Несколько форматов
Отдельный POST на каждый. Например, мастер работает разъездно + в офисе + онлайн — уйдёт **три**
запроса с телами из п.1, п.2 и п.3 соответственно (на один и тот же `{id}`).

## Валидация на фронте (перед отправкой)

Кнопка «Далее»/«Сохранить» блокируется, пока:
- не выбран **ни один** формат; **или**
- выбран **Fixed**, но не заполнены `city`, `street`, `house`; **или**
- выбран **Mobile**, но не выбран ни один город (`cities` пуст).

**Online** самодостаточен — доп. данных не требует.

---

## Что фронт ждёт в ответ (read-путь)

- **Карточки/списки** показывают готовую строку `address.city` как есть (её бэк собирает под любой
  набор форматов — см. `frontend-card-address-output.md`). Префикс «г.» фронт не добавляет.
  Структурированные `street/house/apartment` использует только когда офис — единственный формат.
- **Страница мастера** дополнительно читает `GET /profiles/{id}/work-location` для разбора по полям.
  Эндпоинт возвращает **массив** `WorkLocationView[]` (по записи на формат) — фронт парсит именно массив:
  собирает сегменты адреса по всем форматам (офис → полный адрес, разъездная → регион + города,
  онлайн → «Онлайн»), с фолбэком на `address.city`. Карта: точка по офисной записи + маркеры городов по разъездной.

## Сводка тел по формату

| Формат | `locationType` | Ключевые поля тела |
|---|:---:|---|
| Online | `2` | — (только тип) |
| Fixed | `0` | `country, region, city, street, house, apartment` |
| Mobile | `1` | `country, region, cities[]` |
