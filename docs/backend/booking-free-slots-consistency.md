# Свободные слоты записи: расхождение `days-in-month` и `get-free-slot`

## 1. Симптом (найден на тестировании MVP)

При прямом открытии страницы выбора даты и времени (`/:id/choose-date?serviceId=…`)
на экране **одновременно** оказались:

- список интервалов 15:30–20:00 (чипы выбора времени);
- сообщение «Нет доступных слотов для записи».

Разбор на фронте: сами условия показа взаимоисключающие и написаны верно, поэтому
одновременно они отрисоваться не могут — на экране смешались результаты двух разных
рендеров (SSR и повторного клиентского). Часть причин фронтовые (чиним у себя, см. §5),
но корневое расхождение данных — на стороне контракта, и без правок бэка экран
останется противоречивым: календарь обещает окна, а страница слотов их не находит.

## 2. Что фронт спрашивает сейчас

Экран собирает данные из двух независимых ручек:

```
GET  schedules/days-in-month?year={y}&month={m}&id={profileId}
POST services/get-free-slot/{profileId}
     Body: { duration: number, day: string, dayId: string }
```

| Ручка | Что фронт из неё берёт | Где в коде |
|---|---|---|
| `days-in-month` | `canAdd` → пометка дня в календаре: «есть окна» / «занято» | `src/app/common/calendar/calendar.component.ts:227` |
| `get-free-slot` | массив слотов → чипы времени, либо empty-state | `src/app/profile-ba/components/set-interval-start/set-interval-start.component.ts:59` |

## 3. Проблема №1 — `canAdd` не учитывает длительность услуги

`days-in-month` вызывается **без `serviceId` и без `duration`**
(`src/app/profile-ba/components/choose-date-time/choose-date-time.component.ts:115`) —
их просто негде передать, ручка их не принимает.

Значит `canAdd` отвечает на вопрос «есть ли у мастера хоть сколько-то свободного времени»,
а `get-free-slot` — на вопрос «помещается ли услуга на N минут». Для услуги 60 минут день,
где остались только окна по 30 минут, честно вернёт `canAdd = true` и пустой список слотов.
Пользователь тыкает в день, помеченный «есть окна», и получает «Нет доступных слотов».

**Что нужно:** `days-in-month` должна принимать услугу и считать `canAdd` тем же
алгоритмом, что и `get-free-slot`.

```
GET schedules/days-in-month?year={y}&month={m}&id={profileId}&serviceId={serviceId}
```

- `serviceId` — необязательный, обратная совместимость сохраняется: без него — прежнее
  поведение (есть ли вообще свободное время).
- С `serviceId` — `canAdd = (количество слотов, которые вернёт get-free-slot для этого дня и этой услуги) > 0`.
- Дополнительно просим отдавать `freeSlotsCount: number` — фронт сможет показывать в
  календаре не только «есть/нет», но и «мало окон», и это же поле даёт дешёвый способ
  сверять две ручки в тестах.

Критично: `canAdd` и список слотов должны считаться **одной функцией** в бэкенде, а не
двумя похожими. Любая расхождение в этих двух реализациях снова вылезет как противоречие
на экране.

## 4. Проблема №2 — правило «нельзя записаться менее чем за час» живёт только на фронте

Сейчас фронт сам выкидывает из ответа слоты, до которых осталось меньше часа
(`compareTimeHour`, `src/helpers/dateUtils/dateUtils.ts:168`), и делает это по времени
той машины, где выполняется код. При серверном рендере это время сервера (UTC),
в браузере — время пользователя. Один и тот же ответ бэка превращается в два разных
списка — это и есть непосредственная причина противоречивого экрана.

Фронт этот фильтр убирает. Взамен нужно, чтобы `get-free-slot` **сам** не возвращал:

1. слоты, которые уже прошли;
2. слоты внутри минимального лид-тайма (сейчас де-факто 60 минут — подтвердите значение
   или, лучше, сделайте его настройкой профиля и отдавайте в ответе);
3. слоты за прошедшие даты целиком.

Считать — в таймзоне бизнеса. Фронт для записи фиксирует `Europe/Moscow`
(`src/app/profile-ba/helpers/booking-date.ts:1`), бэк должен использовать её же
(или отдавать таймзону профиля в ответе, тогда фронт подхватит).

Заодно про формат даты: фронт сейчас шлёт `day` как `"Tue Jul 28 2026"` (`Date.toDateString()`) —
формат зависит от локали рантайма и не содержит таймзоны. Мы переходим на ISO-дату
`"2026-07-28"`. Просьба принимать оба варианта в переходный период, а в новом коде
опираться на ISO и на `dayId`.

## 5. Проблема №3 — пустой массив не объясняет, почему он пустой

Сейчас `get-free-slot` возвращает голый массив. `[]` может значить пять разных вещей,
и фронт вынужден на все случаи показывать одинаковое «Нет доступных слотов для записи»,
даже когда честный ответ — «на сегодня поздно, посмотрите завтра».

Просим завернуть ответ (или добавить поля рядом, если ломать формат нельзя):

```jsonc
{
  "slots": [
    { "start": "15:30", "end": "16:30" },
    { "start": "16:00", "end": "17:00" }
  ],
  "reason": null,          // заполняется только когда slots пуст
  "timezone": "Europe/Moscow",
  "minLeadTimeMinutes": 60
}
```

Допустимые значения `reason`, когда `slots` пуст:

| `reason` | Смысл | Что покажет фронт |
|---|---|---|
| `not_working_day` | день не рабочий по графику | «В этот день мастер не работает» |
| `day_passed` | дата уже прошла | день вообще не должен быть кликабельным |
| `too_late_today` | слоты на сегодня были, но лид-тайм уже вышел | «На сегодня запись закрыта — выберите другой день» |
| `fully_booked` | рабочий день, всё занято | «Все окна заняты» |
| `service_too_long` | свободные промежутки есть, но услуга в них не помещается | «Для этой услуги нужно больше времени, выберите другой день» |

Время слотов — строкой `HH:mm` в таймзоне из поля `timezone`. Сейчас приходит
`start` в разных видах (фронт режет строку до `HH:mm` вручную,
`toHoursMinutesString`) — просим зафиксировать один формат.

## 6.1. Ответы на открытые вопросы бэка

**Лид-тайм на уровне мастера.** Поправка к сказанному 29.07: `minLeadTimeMinutes`
(как и `utcOffsetMinutes`) сейчас только маппится в DTO (`schedule.service.ts:70`) и
**нигде не читается** — проверено `grep` по `app/` и `services/`, ни одного обращения к
полю. Фронт не хардкодит лид-тайм, но и не показывает его пользователю; он полностью
доверяет тому, что бэк уже вырезал непроходящие по лид-тайму слоты из `slots` и объяснил
пустой ответ через `reason: "too_late_today"`. Так что менять на фронте всё равно не
придётся, но раньше был не пустой список дел, а закрытая задача — по факту работать с
`minLeadTimeMinutes` ещё только предстоит, если понадобится показывать его в UI. Само
продуктовое решение (нужна ли настройка на уровне мастера, 60 минут одинаково не подходит
маникюру и выездной услуге) не меняется.

**Корзина из нескольких услуг.** Сейчас по факту так:

- клиентская запись (`choose-date`) — **всегда одна услуга**, `duration` берётся из неё
  (`service.duration`), корзины на этом экране нет;
- мастер, добавляющий запись руками, суммирует длительности выбранных услуг
  (`getPrice`, `src/helpers/common/price.helpers.ts:17`) и шлёт сумму одним числом.

То есть суммарный `duration` вас устраивает ровно до тех пор, пока между услугами не нужны
перерывы или разные исполнители. Как только появится клиентская корзина — вернёмся с
отдельной постановкой, там нужен будет список услуг, а не одно число.

## 7. Как проверить, что починено

1. Услуга длительностью 60 минут, у мастера на день остались только окна 30 минут.
   Ожидаемо: день в календаре помечен как «занято», `canAdd = false`, при клике —
   `reason: "service_too_long"`, и **никаких** чипов времени.
2. Сегодня, текущее время 19:10, рабочий день до 20:00, лид-тайм 60 минут.
   Ожидаемо: `get-free-slot` возвращает `slots: []` и `reason: "too_late_today"`
   независимо от таймзоны вызывающего; в календаре день не помечен «есть окна».
3. Один и тот же запрос из UTC-окружения и из MSK-окружения возвращает **идентичный**
   список слотов.
4. Для любого дня месяца: `canAdd === (get-free-slot-detailed для этого дня вернул непустой slots)`
   — при условии, что в оба запроса передана одна и та же услуга. Это инвариант, его стоит
   закрыть автотестом на стороне бэка (у нас юнит-тестов в проекте нет).

## 7.0. Найдено при тесте 30.07.2026: `daysOfWork` теряет день у клиентов западнее UTC

`days-in-month` отдаёт `daysOfWork` как абсолютный инстант в MSK-нотации, например
`2026-07-31T03:00:00+03:00` — это `2026-07-31T00:00:00Z`, то есть полночь UTC того дня,
сериализованная со смещением Москвы (отсюда и «03:00», а не «00:00»).

Фронт до сих пор читал этот день локальными геттерами (`getFullYear/getMonth/getDate`)
на объекте `Date`. Эти геттеры используют таймзону **браузера клиента**, а не Москвы.
На клиенте с таймзоной западнее UTC (например UTC−4) тот же инстант — уже предыдущий
локальный день, и `31 июля` в календаре показывался как `30 июля`, `1 августа` — как
`31 июля`, и так по всему месяцу.

**Починили на фронте:** день теперь достаётся из UTC-компонентов инстанта
(`getUTCFullYear/getUTCMonth/getUTCDate`), которые всегда совпадают с намерением бэка,
независимо от таймзоны браузера — `toBusinessCalendarDate()` в `dateUtils.ts`, подключено
в `normalizeDaysInMonthRow` (`schedule.service.ts`) и в двух местах кабинета БА
(`cabinet-ba.component.ts`, `modal-calendar.component.ts`), где `daysOfWork` читался так же.

**Просьба к бэку:** по возможности отдавать день без обёртки в конкретную таймзону —
либо чистой датой `"2026-07-31"`, либо явной UTC-полночью `"2026-07-31T00:00:00Z"`.
Текущий формат (UTC-полночь, но с `+03:00` в самой строке) рабочий, но лишний повод для
таких багов при следующей правке — календарный день и инстант лучше не смешивать.

## 7.1. Открытый вопрос после теста 29.07.2026: `id` строк `days-in-month`

Фронт использует `id` строки `days-in-month` как `dayId` и шлёт его в `get-free-slot-detailed`,
а затем в создание записи (`daysOfScheduleId`). Если для будущих месяцев строки расписания
ещё не материализованы и `id` приходит пустым/`null`, вся ветка записи обрывается молча.

Просим подтвердить инвариант: **любая строка `days-in-month` с `canAdd = true` обязана иметь
непустой `id`, пригодный и для `get-free-slot-detailed`, и для создания записи.** Если это
не так — нужен явный признак в ответе, а не пустая строка.

Фронт со своей стороны больше не молчит: без `dayId` слоты запрашиваются по ISO-дате
(запасной ключ из §4), и если ручка при этом вернёт непустой `slots`, экран покажет ошибку,
а не чипы времени, которые всё равно нельзя отправить.

Фронтовая часть проверяется теми же четырьмя сценариями плюс:

5. Прямое открытие `/:id/choose-date?serviceId=…` (полная загрузка, не переход внутри SPA)
   в 19:10 при рабочем дне до 20:00 — на экране ровно одно состояние. Именно этот сценарий
   давал исходный баг.
6. Экран БА «Добавить запись»: слоты по-прежнему показываются целиком, включая ближайший час.

## 8. Ответ фронта на `BACKEND-TIMEZONE-PLAN-2026-07-30.md`

### 8.1. Фикс из §7.0 не конфликтует с целевой семантикой шага 4

Целевое правило бэка — «`DaysOfWork` = UTC-полночь календарного дня бизнеса, дата это дата,
а не момент» — это ровно то, что уже наблюдается в проде (пример из отчёта тестировщика:
`2026-07-31T03:00:00+03:00` = `2026-07-31T00:00:00Z`, точная полночь UTC, `not_midnight`
по вашей диагностике 0.3 для таких строк — `0`). Значит `toBusinessCalendarDate()`
(UTC-компоненты инстанта) уже читает именно то, что бэк планирует зафиксировать как
инвариант. Если по факту на части старых строк `not_midnight > 0` и вы сделаете бэкфилл
из §4 — на фронте ничего менять не придётся, бэкфилл только исправит данные, которые
и так читались как «намерение бэка», просто для части строк это намерение было записано
некорректно.

### 8.2. Ответ на 0.4 — что фронт кладёт в `timeZone` при регистрации бизнес-профиля

Подтверждаем находку из раздела 0-Р: единственное место, которое пишет это поле —
`register-business-profile.component.ts:261`:
```ts
timeZone: new Date().getTimezoneOffset()   // -180 для MSK — минуты, запад-положительный
```
Проверили отдельно: при **обновлении** профиля (`main-profile`, `column-baprofile` и другие
формы редактирования бизнес-профиля) поле `timeZone` фронт не отправляет вообще — только
при первичной регистрации. Так что после регистрации значение в БД зафиксировано навсегда
уже сейчас, без всякого закомментированного кода в `UpdateProfile` (это и есть проблема №3
из вашего раздела 1 — мастер, переехавший в другой часовой пояс, не может её поправить,
подтверждаем с фронтовой стороны).

Про `utcOffsetMinutes` в ответе `get-free-slot-detailed` — **фронт его не читает.** Не
только не читает `Booking:TimeZone`-дефолт (это мы и раньше знали), а вообще нигде не
обращается к полю после маппинга в DTO: `grep` по `app/` и `services/` — ноль совпадений
за пределами `schedule.service.ts:69`. Мы поправили и свой собственный документ (§6.1
выше) — там раньше было написано обратное. Практический вывод для вас совпадает с вашим
собственным: `-10800 → +180` ничего на фронте не сломает, можно чинить не оглядываясь на
клиентов этого поля, потому что клиентов нет.

### 8.4. Важно: живой риск бронирования прошедших слотов уже сейчас, не только «после шага 2»

Из вашего раздела 0-Р следует, что на проде **прямо сейчас** `GetBusinessUtcOffsetHoursAsync`
возвращает `-180` и трактуется как часы, то есть `SlotCalculator` сравнивает с «сейчас»,
которое on 7.5 суток в прошлом. Это значит `too_late_today` недостижим и лид-тайм не
применяется — уже сегодня, не после какого-то будущего изменения.

С фронта мы в этом же тестировании убрали клиентский фильтр по времени (`compareTimeHour`)
и полностью доверились серверной фильтрации — это было осознанное решение, задокументированное
в §4 этого файла, и оно было правильным для проблемы, которую мы тогда чинили (расхождение
SSR/CSR по локальному времени). Но это решение опиралось на то, что серверная фильтрация
вообще что-то фильтрует. Если ваш разбор верен, сейчас клиент технически может выбрать и
подтвердить уже прошедший слот сегодняшнего дня — фронт это никак не поймает.

**Вернули временный предохранитель** — но не старую реализацию: та была на `Date` в
локальной зоне браузера, и именно это дало исходный SSR/CSR баг. Новая версия детерминирована
независимо от таймзоны хоста — `nowInBookingTimezone()`/`isPastBookingSlot()`
(`app/profile-ba/helpers/booking-date.ts`) берут «сейчас» через `Intl.DateTimeFormat` с
жёстко заданной `Europe/Moscow`, а не через `new Date()`/`getTimezoneOffset()`. Слот и текущий

продуктовым вопросом (§6.1), и фронту не стоит его домысливать. Работает только для

именно в `normalizeDaysInMonthRow` (`services/schedule.service.ts`), то есть покрывает
