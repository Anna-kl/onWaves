# Мессенджеры клиента в календаре БА — что нужно от бэкенда

Фронт уже реализован. Чтобы в карточках клиентов календаря БА заработали кнопки
**MAX / Telegram**, бэкенду нужно отдавать контакты клиента в ответе расписания.
Ниже — полный контракт.

Родственный документ: [`docs/max-messenger-backend.md`](../max-messenger-backend.md) — то же самое,
но про поле `max` у **бизнес-профиля** (карточка мастера). Здесь — про **клиента**.

## 1. Контекст: что показывает фронт

Экран: календарь БА, роут `notes/:id` (`BANotesComponent`). В карточке каждой записи есть
блок связи с клиентом. Логика показа кнопок сейчас такая:

| Условие | Что показываем |
|---|---|
| пришёл `max` | кнопка «MAX» → `https://max.ru/…` |
| пришёл `telegram` | кнопка «Telegram» → `https://t.me/…` |
| не пришло ни одного | кнопка «SMS» → `sms:+<phone>` |

Кнопка «Позвонить» (`tel:`) показывается всегда, она уже работает по `phone`.

**Канал считается подключённым только если бэк прислал контакт.** Достраивать канал из
номера телефона фронт намеренно не будет:

- у **MAX** ссылки по номеру нет в принципе (в отличие от `wa.me`) — только username или
  ссылка вида `https://max.ru/u/<хеш>`;
- `https://t.me/+<phone>` формально открывается, но у клиента без Telegram показывает пустой
  чат. Мастер думает, что написал, а сообщение никто не получает. Раньше эта кнопка стояла
  безусловно на каждой карточке — это и был баг, который мы чиним.

Поэтому пустое поле = кнопки нет = уходим в SMS.

## 2. Что добавить в ответ

Ручки расписания БА:

```
POST schedules/get-ba-schedule/{profileId}
POST schedules/get-ba-canceled-schedule/{profileId}
Body: IViewDateSchedule
```

Обе возвращают массив записей (`IViewScheduleBA`). В **каждый элемент** массива добавить два
необязательных поля рядом с уже существующим `phone`:

| Поле | Тип | Значение |
|---|---|---|
| `telegram` | `string`, nullable | контакт клиента в Telegram: `@user`, `user`, `t.me/user`, `https://t.me/…`, либо `+79001234567` |
| `max` | `string`, nullable | контакт клиента в MAX: `@user`, `user`, `max.ru/u/<хеш>`, `https://max.ru/…` |

Формат ввода фронт **не навязывает**: отдавайте строку как есть, нормализацию в URL делает
`src/helpers/common/messenger.ts`. Пустую строку лучше отдавать как `null` (фронт трактует
`null`, `undefined` и `""` одинаково — «канал не подключён»).

Важно про телефон: для `telegram` номер — валидное значение (`t.me/+7900…` работает), для
`max` — **нет**. Если в MAX-поле окажется голый номер, фронт его отбракует и кнопку не покажет.
Не подставляйте телефон в `max` в качестве заглушки.

## 3. Откуда брать значения

Клиенты в системе бывают двух видов, и оба нужно покрыть:

1. **Зарегистрированный клиент** — у него есть профиль. Берём контакты из профиля клиента
   (те же поля, что у бизнес-профиля: `telegram`, `max`).
2. **Клиент, заведённый мастером вручную** (запись по имени + телефону) — контактов может не
   быть вовсе. Тогда просто `null` в обоих полях, фронт покажет SMS.

Если у клиента канал подключён к боту уведомлений, но username/ссылки нет — прислать поле
всё равно нечем: ссылку на чат из подписки на бота не построить. В этом случае корректно
вернуть `null` (фронт покажет SMS), а не пытаться подставить что-то синтетическое.

## 4. Пример ответа

```json
[
  {
    "recordId": "5f2c1b7e-...",
    "name": "Анна",
    "phone": "79001234567",
    "telegram": "@anna_k",
    "max": "https://max.ru/u/AbC123xyz",
    "start": "2026-07-28T10:00:00",
    "duration": 60,
    "status": 1,
    "services": []
  },
  {
    "recordId": "9a71d0c4-...",
    "name": "Клиент без мессенджеров",
    "phone": "79007654321",
    "telegram": null,
    "max": null,
    "start": "2026-07-28T12:00:00",
    "duration": 30,
    "status": 1,
    "services": []
  }
]
```

Первая карточка покажет MAX + Telegram, вторая — SMS.

## 5. Персональные данные

Контакты клиента в мессенджерах — ПДн, и здесь они передаются **третьему лицу** (мастеру),
а не самому субъекту. В проекте уже есть механизм согласий (`ConsentService`,
`Consent/{profileUserId}`, каналы `Telegram = 1`, `Max = 5`). Прежде чем отдавать эти поля,
проверьте на своей стороне, что клиент согласие давал, и не отдавайте контакты без него.
Фронт эту проверку сделать не может — он видит только то, что вы прислали.

## 6. Альтернатива, если поля добавить нельзя

Если расширять `get-ba-schedule` не хочется, второй рабочий вариант — отдать в записи
`clientId` (id профиля клиента). Тогда фронт сможет сам сходить в уже существующую ручку:

```
GET profiles/messenger-channels-status/{profileUserId}   →  { telegram, vk, max }
```

Но она отвечает только «подключён / не подключён», без username — ссылку на чат по ней не
построить, кнопка сможет вести максимум на `t.me/+phone` со всеми оговорками из §1. Плюс это
+N запросов на каждый рендер календаря. **Вариант с полями в §2 предпочтительнее.**

## 7. Чек-лист для бэка

- [ ] Добавить nullable `telegram` и `max` в DTO записи расписания БА (`IViewScheduleBA`).
- [ ] Заполнять их из профиля клиента, если клиент зарегистрирован; иначе `null`.
- [ ] Вернуть оба поля в `POST schedules/get-ba-schedule/{profileId}`.
- [ ] Вернуть оба поля в `POST schedules/get-ba-canceled-schedule/{profileId}`.
- [ ] Не подставлять телефон в поле `max` — ссылки по номеру у MAX нет.
- [ ] Проверить наличие согласия клиента перед отдачей контактов (§5).

## 8. Что уже сделано на фронте (для сверки)

- поля `telegram` / `max` в `src/app/DTO/views/schedule/IViewScheduleBA.ts`;
- общий разбор ссылок `src/helpers/common/messenger.ts`
  (`getMaxUrl`, `getTelegramUrl`, `getSmsUrl`, `getTelUrl`);
- методы `clientMaxHref` / `clientTelegramHref` / `clientSmsHref` / `clientTelHref` в
  `src/app/profile-ba/notes/ba-notes/ba-notes.component.ts`;
- кнопки MAX / Telegram / SMS с иконками в обоих блоках контактов
  `src/app/profile-ba/notes/ba-notes/ba-notes.component.html`.

До появления полей на бэке все карточки будут показывать SMS — это ожидаемое поведение
(канал не подтверждён → не показываем), а не поломка фронта.
