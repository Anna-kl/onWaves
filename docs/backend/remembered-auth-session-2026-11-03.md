# Запоминание авторизации — 03.11.2026

Реализовано в исходниках Angular и `D:/Project/OcpioServer`. Выкладка в прод не выполнялась.

## Поведение

- Клиент и мастер остаются в аккаунте после закрытия браузера и истечения JWT. Повторный вход нужен после 30 дней подряд без активности или после явного выхода.
- Срок скользящий: успешное восстановление и запросы с действующим JWT обновляют серверный `Sessions.LastRequest`. Обычный API ограничивает запись активности одним обновлением за пять минут.
- Cookies `auth-token-ocpio`, `uuid-ocpio`, `profileId-ocpio` сохраняются на 30 дней от успешного продления. JWT остаётся со своим сроком из `Jwt:ExpiresInHours` (по умолчанию 72 часа).
- Действие пользователя или возврат в видимую вкладку запускает тихое продление не чаще раза в пять минут. Отдельного фонового таймера нет.
- Истекающий JWT обновляется перед защищённым запросом; при HTTP 401 предусмотрено одно обновление и один повтор. Параллельные запросы используют общее продление. Bearer задают прежние HTTP-сервисы.
- Ошибка сети не стирает cookies. После возврата сети восстанавливаются и токен, и профиль. Ответ старого запроса после выхода или смены аккаунта не восстанавливает прежнюю сессию; старый запрос не повторяется от имени нового аккаунта.
- Инициализация роутера ждёт загрузки выбранного профиля в NgRx. Если cookie профиля отсутствует, выбирается основной профиль с сервера.
- SSR остаётся анонимным, персональная сессия на сервере Angular не восстанавливается.

## API и проверка прав

`POST /v1/api/auths/uuid`: прежнее тело `{ token, uuid }` и прежний успешный ответ `{ code: 200, data: { token, profile }, message: sessionId }`.

Этот метод отдельно проверяет подпись HS256, issuer, audience, наличие exp и допустимость nbf прежнего JWT. Истечение exp допускается только для восстановления: оно не разрешает доступ к обычному API. Возможность восстановления определяют успешная сессия в БД, её UUID, активный Auth и `LastRequest` менее 30 дней назад. Профиль берётся из этой сессии и должен принадлежать тому же AuthId. Неверные/просроченные данные дают бизнес-код 401; профиль, которого больше нет, — 404.

Существующий подписанный JWT вместе с UUID используется как удостоверение для продления этой же серверной сессии. Отдельный refresh-token и новая таблица в этом изменении не вводятся. Хранение JWT в JS-cookie остаётся прежним; переход на HttpOnly требует отдельного контракта.

`POST /v1/api/auths/logout`: тело `{ token, uuid }`. Отзывает только предъявленную сессию устройства через `SessionStatus.Expired`; ответ идемпотентный `code: 200`. Повторное использование её JWT и продление отклоняются. Локальные cookies удаляются сразу, даже при недоступном сервере.

На обычном API `ValidateLifetime=true`. После проверки JWT обработчик `OnTokenValidated` дополнительно проверяет состояние сессии и Auth и обновляет активность. Для `uuid` и `logout` этот обработчик не меняет дату до проверки тела запроса.

Email-вход теперь сохраняет UUID и успешный статус. Старые email-сессии с подписанным JWT, профилем и статусом Created поддерживаются; отсутствующий UUID привязывается после проверки подписи. Гостевая регистрация использует тот же механизм сохранения cookies.

`GET profiles/get-for-edit-baprofile/{id}` теперь требует JWT и владение профилем. Чтение больше не выпускает JWT последней сессии аккаунта и не меняет сессию другого устройства. Angular передаёт Bearer явно и использует текущий токен из cookie.

## Выкладка

1. Сначала .NET API, затем фронтенд. Старый API не умеет восстанавливать JWT после истечения его срока.
2. Миграции БД для этого изменения не нужны: используются существующие `Sessions.LastRequest`, UUID и Status.
3. Проверить в браузере клиентский и бизнес-профиль: вход, F5, закрытие/возврат, переключение профиля, запись, выход и повторный заход. Работающий браузер должен загрузить новую сборку фронтенда.
4. На тестовой сессии проверить LastRequest за 29 и 31 день назад. Проводить такую проверку на тестовом аккаунте.

## Автоматические проверки

- Front: `npm run test:auth` — ChromeHeadless с HTTP-заглушками; параллельные запросы, устаревший JWT, выход, смена аккаунта, потеря выбора профиля, гостевая регистрация, SSR и сбой сети. При необходимости задать `CHROME_BIN`.
- Backend: `dotnet test ServicesClient.Tests/ServicesClient.Tests.csproj --filter FullyQualifiedName~RememberedSessionTests --output .testout-auth` из `D:/Project/OcpioServer`. Отдельный output позволяет не перезаписывать DLL запущенного отладчика.
- Проверка типов: `npx tsc --noEmit -p tsconfig.app.json` и `npx tsc --noEmit -p tsconfig.auth-spec.json`.

Общий `npm test` сейчас блокируется URL карты в scripts-конфигурации и старыми CLI-spec. `test:auth` запускает нужные проверки через Angular Architect без внешних скриптов и без изменения общей конфигурации.

Результат локальной проверки: 23 серверных теста и 17 тестов ChromeHeadless прошли; полная браузерная сборка development и серверная сборка production прошли. На проде сценарий с реальным аккаунтом не проверялся.
