# Запрос к backend — форматы выполнения услуги + адрес клиента при записи

Дата: 2026-07-19
От: фронт. Нужно, чтобы бэк внёс изменения (ниже — контракт, который ждёт фронт).

> ✅ **РЕАЛИЗОВАНО бэком** (см. `FRONTEND-CHANGES-2026-07-19-service-location.md`). Итоговые имена
> отличаются от предложенных ниже — фронт приведён к ним:
> - услуга: поле называется **`workLocationType`** (скаляр `WorkLocationType`);
> - запись: поле называется **`location`** (`RecordLocationView`: `locationType, country, region,
>   city, street, house, apartment, comment, longitude, latitude, onlineLink`) — дом называется
>   **`house`**, есть `comment`/`onlineLink`;
> - правило: услуги **одного характера** в одной записи (иначе 400);
> - выезд → фронт шлёт адрес клиента; на месте/онлайн/legacy → `location: null` (бэк заполняет сам).
>
> Разделы ниже оставлены как история запроса.

## Зачем

1. При создании/редактировании услуги БА выбирает, **в каких форматах** эта услуга оказывается:
   фиксированное место / разъездная (выезд) / онлайн. Доступные варианты берутся из **форматов работы
   профиля** (`GET profiles/{id}/work-location`) — услуга не может иметь формат, которого нет у профиля.
2. При записи на **разъездную** услугу клиент обязан указать **свой адрес** (куда выезжает мастер).
   Это должно работать во всех сценариях записи (гость, авторизованный, запись от БА).

Сейчас ни `Service`, ни `Record` таких полей не имеют — отсюда запрос.

## Изменение 1. Формат выполнения на услуге — `locationType`

> Решение продукта: услуга оказывается **ровно в одном** формате (на UI — radiobutton).
> Поэтому поле **скалярное**, не массив.

### 1.1. Модель услуги
Добавить в услугу одно поле:

```jsonc
{
  "id": "…",
  "name": "Маникюр",
  "paymentForType": 0,
  "price": { … },
  "duration": 60,
  "locationType": 1   // ← НОВОЕ: 0 Fixed | 1 Mobile | 2 Online
}
```

- Тип: `WorkLocationType` (число `0|1|2`), nullable.
- `null` трактуем как «не задано» (обратная совместимость со старыми услугами) —
  фронт в этом случае покажет адрес БА как раньше.

### 1.2. Где вернуть `locationType` (read)
Во всех методах, отдающих услуги:
- `GET services/get-by-group/{groupId}` → `Service[]`
- `GET services/without-group/{profileId}` → `Service[]`
- (и всё, что агрегирует услуги: `get-images`, выборки для записи и т.п.)

### 1.3. Где принять `locationType` (write)
- `POST services/` (`saveService`) — тело = объект `Service`, теперь с полем `locationType`.
  Один эндпоинт и на create, и на update.

### 1.4. Валидация на бэке
- `locationType` ∈ форматов профиля (`work-location` этого `profileUserId`). Если БА прислал формат,
  которого нет у профиля, — `400`.
- Для новых услуг поле обязательно (фронт и так не даст сохранить без выбора); `null` допускается
  только у старых услуг.

> Справочник доступных форматов для UI создания услуги фронт берёт из **существующего**
> `GET profiles/{id}/work-location` (массив записей по формату). **Новый эндпоинт не нужен.**

## Изменение 2. Адрес клиента при записи — `clientAddress`

### 2.1. Модель записи (`Record`)
Добавить в тело записи адрес клиента (нужен только для разъездных услуг):

```jsonc
{
  "daysOfScheduleId": "…",
  "start": "12:30:00",
  "services": [ … ],
  "clientId": "…",          // может отсутствовать у гостя до регистрации
  "comment": "…",
  "clientAddress": {         // ← НОВОЕ (nullable)
    "country": "Россия",
    "region": "Московская область",
    "city": "Химки",
    "street": "Ленинский проспект",
    "home": "15",            // ⚠️ фронтовый ViewAddress использует "home", не "house"
    "apartment": "305"
  }
}
```

Форма адреса = фронтовый `IViewAddress`: `country, region, city, street, home, apartment`.
⚠️ Обратите внимание: поле дома здесь называется **`home`** (в отличие от work-location, где было
`house`). Если бэку удобнее единое имя — скажите, приведём фронт к нему.

### 2.2. Где принять
- `POST records/add-user/{id}` (`saveRecord`) — основной путь и для гостя, и для авторизованного.
- Если запись создаётся другими путями (запись от БА, `confirm-record2`, notes/add-record) — там же
  принять `clientAddress` в теле.

### 2.3. Валидация на бэке
- Если хотя бы одна услуга из `services` имеет `locationType === Mobile (1)` → `clientAddress`
  обязателен (минимум city + street + house). Иначе `400`.
- Для фиксированной/онлайн услуги `clientAddress` игнорируется/не требуется.

> Фронт продублирует эту валидацию в UI (не даст отправить без адреса), но серверная проверка нужна
> как источник истины.

## Что меняет фронт (для сверки контракта)

Ниже — что фронт **будет слать и читать**, чтобы бэк подогнал модель ровно под это.

### DTO (TypeScript), которые расширяет фронт
```ts
// Service / subGroup — новое поле:
locationType?: WorkLocationType;   // 0 Fixed | 1 Mobile | 2 Online

// Record — новое поле:
clientAddress?: {
  country: string|null; region: string|null; city: string|null;
  street: string|null; house: string|null; apartment: string|null;
};
```

### Создание/редактирование услуги
- В формах услуги (`arenda-service`, `arenda-hour`) добавляется **radiobutton** «Как оказывается услуга»
  с вариантами, которые фронт берёт из `GET profiles/{id}/work-location` (показываются только форматы,
  реально настроенные у профиля). Выбор — ровно один.
- В `POST services/` фронт добавит `locationType: <0|1|2>` в тело `Service`.

### Запись (все сценарии)
- Фронт вычисляет `isMobile = services.some(s => s.locationType === 1)`.
- Если `isMobile` — на экране записи (и в гостевой форме, и у авторизованного, и при записи от БА)
  появляется **обязательный** блок адреса клиента; без него отправка блокируется.
- В `POST records/add-user/{id}` фронт добавит `clientAddress: { … }` (только когда `isMobile`).
